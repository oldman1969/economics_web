## 1. 五类工具：感知/执行/协作/事件触发/用户沟通

按两个特征审视：**调用方向**（谁发起）+ **作用对象**（作用于什么）。

| 工具类型 | 调用方向 | 作用对象 | 例子 |
|----------|----------|----------|------|
| 感知工具 | Agent 主动调用 | 获取信息 | web_search、read_file、grep_file |
| 执行工具 | Agent 主动调用 | 改变世界 | shell_exec、write_file、send_email |
| 协作工具 | Agent 主动调用 | 驱动其他 Agent/人类 | spawn_subagent、send_message |
| 事件触发工具 | **Agent 注册、外部触发** | 驱动 Agent 开始执行 | set_timer、monitor_shell |
| 用户沟通工具 | Agent 主动调用 | 向用户传递信息 | reply_to_user、send_notification |

> 💡 关键区别：**感知/执行/协作**由 Agent 主动调用，**事件触发**是外部世界反向驱动 Agent。没有事件触发工具，Agent 只能被动响应，无法在指定时间自主行动。

## 2. 工具设计的通用原则

### 2.1 能力表达形式：专用工具 vs Skill + 通用执行器

| 形态 | 特点 | 适用 |
|------|------|------|
| 专用代码工具 | 结构化、可测试，但占数百 token、数量膨胀破坏 KV Cache | 稳定底层操作 |
| Skill + 通用执行器 | 自然语言文档 + 终端/代码解释器执行，少量工具覆盖大量场景 | 频繁变化的能力 |

**三维决策框架**：参数复杂度（复杂→专用 schema）、变更频率（频繁→Skill）、模型能力（SOTA→Skill，弱模型→专用 schema）。

### 2.2 工具粒度：整合与分离

判断标准：**功能相似性 + 使用场景重叠度**。

- 应整合：`extract_pdf_text`、`extract_docx_content`、`extract_pptx_content` → 统一的 `read_document(file_type=...)`
- 不该整合：图片 OCR 和视频关键帧提取虽都"内容提取"，但参数形态、延迟差异大

> 工具超过 100 个时，最先进模型也会选错。整合降低认知负担。

### 2.3 通用性设计

**通用工具优于专用工具**（除非安全/权限/性能理由）——给 Agent 一个 Python 解释器，等于给它"元能力"，能处理没预料到的边缘场景。但需特殊权限的操作（生产数据库写）要专用工具。

### 2.4 工具设计演进（三代）

```
第一代: 直接 API 封装（粒度细，需协调多工具）
第二代: ACI（工具对应 Agent 目标而非底层 API）
第三代: 三个问题——如何准确调用（示例驱动）、如何发现（动态发现）、如何串联（代码编排）
```

> 💡 代码编排的精髓：LLM 一次性生成脚本，中间变量留在执行环境，只有最终结果返回上下文——**token 消耗可降两个数量级**（第 5 章展开）。

## 3. 工具描述的艺术：ACI 的落地

### 3.1 核心：写"什么时候用"，不是"能做什么"

| 差 | 好 |
|----|----|
| "搜索相关内容" | "当需要获取实时信息或查找未知事实时使用" |

### 3.2 边界比能力更重要

> **大多数工具调用失败的根因，不是模型不知道工具能做什么，而是不知道工具不能做什么。**

文件搜索工具要写明"只能基于文件名匹配，不能搜文件内容"——否则模型会去猜。

### 3.3 参数用具体例子代替抽象规范

```
坏: "timestamp: RFC3339 格式"
好: "timestamp: RFC3339 格式，例如 2024-03-15T14:30:00Z"

坏: "phone: E.164 格式"
好: "phone: E.164 格式（国家代码+号码，无空格），例如 +8613888888888"
```

### 3.4 附带调用示例

JSON Schema 只能描述类型，无法表达"时间戳是秒还是毫秒、过滤条件如何嵌套"这些隐式约定。**加 1-5 个真实示例，准确率从 ~72% 提升到 ~90%。**

### 3.5 一条实用调试原则

> 当 Agent 频繁选错工具时，**优先检查工具描述，而不是怀疑模型能力**。修正描述的投入产出比，远高于换更强的模型。

## 4. 参数传递的保真性：静默转换的反模式

比功能缺失更隐蔽的，是工具在执行前**悄悄"修正"模型输入**：

### 4.1 静默输入转换

Cursor 某版本把中文弯引号（`“`）静默转成英文直引号（`"`）。结果：模型读到文件里是弯引号，原样传入 `old_string`，但参数层已转成直引号 → 匹配失败 → 模型反复重试，无法理解"为什么我明明看到的却找不到"。

### 4.2 静默参数注入

某 IDE 的 bash 工具对所有 `git commit` 自动附加一个标记参数，旧版本 Git 不支持 → 模型反复调整措辞都失败。

### 4.3 根本原则

> **模型感知到的世界与工具操作的世界之间，不能存在系统性偏差。** 参数传递必须透明，若需规范化，必须在描述中说明、在返回中告知。

## 5. MCP：工具生态与安全风险

### 5.1 MCP 是什么

Anthropic 2024 年底发布的开放标准，统一 AI 模型与外部工具的通信——"为 AI 工具生态制定通用的插座标准"。

- **客户端-服务器架构**：MCP 服务器暴露工具，客户端（Agent 框架/IDE）标准化通信
- **三类原语**：工具（可执行操作）、资源（只读数据）、提示模板（可复用提示词）
- **价值**：一次开发，处处可用（Cursor、Claude Desktop、OpenClaw 通用）

### 5.2 三个递进挑战

1. **同步调用限制** —— MCP 主体是请求-响应，无法唤醒未运行的 Agent（需在协议之上构建事件驱动）
2. **上下文开销** —— 仅 5 个 MCP 服务器就可能引入 ~55,000 token 工具定义，200K 窗口用掉近三成。缓解：只给工具名称索引，需要时再查（Cursor 实测 token 消耗降 46.9%）
3. **能力沉淀为知识** —— 工具过多时，Skills 把"工具选择"转化为"知识检索"

### 5.3 四大安全风险

| 风险 | 说明 |
|------|------|
| **工具描述投毒** | 恶意服务器在 description 里夹带指令（提示注入的变种，载体从用户输入换成工具定义） |
| 恶意/被劫持服务器 | 供应链攻击、远程入侵篡改 |
| 同名工具遮蔽 | 恶意服务器遮蔽正规工具，诱导调用路由到攻击者 |
| 凭证管理 | Agent 持有的 OAuth/API key 被诱导滥用 |

> 缓解：把 description 当**不可信输入**审计、锁定版本、最小权限凭证、Sidecar 独立审查。第五章将引入 Simon Willison 的"致命三要素"框架（访问私有数据 + 暴露不可信内容 + 对外通信）。

## 6. 事件驱动的异步 Agent

### 6.1 训练同步 / 部署异步的根本矛盾

> LLM 训练范式假设**同步**（发工具调用后，下一条必须是工具结果）；真实部署要求**异步**（用户随时打断、多任务并发、外部事件随时到达）。这个矛盾贯穿后续所有工程取舍。

### 6.2 为什么异步

同步 Agent 像"只会排队的柜台"，异步像"灵活的秘书"——多事项并行，按紧急度调度，可暂停切换。三大能力：

1. 异步执行是常态（长任务不阻塞用户交互）
2. 事件优先级动态判断（取消/入队/并行）
3. 中断和恢复的流畅性

### 6.3 OpenClaw 的局限与 PineClaw 的突破

- **OpenClaw**：Cron（定时）+ Heartbeat（心跳轮询）+ Hooks（生命周期）——但都是**时间驱动**，对第三方事件源（新邮件、API 回调）缺乏即时接入，只能等下一个轮询周期
- **PineClaw**（Pine AI 的打电话插件）：引入 **Channel 机制**，在 Gateway 和 Pine API 间建立实时事件通道，响应从分钟级降到秒级

> 💡 核心价值：**真正的"主动服务"不仅需要 Agent 定时检查世界，更需要世界主动通知 Agent。**

### 6.4 架构：一切都是事件流

所有输入（用户消息、工具返回、外部回调、定时触发）统一建模为**事件流**，事件队列 + 路由器判定紧急度 + LLM 推理循环。

## 7. 主动工具发现

工具从十几个涨到上千，如何找到需要的那个？

| 方法 | 做法 | 局限 |
|------|------|------|
| 检索预筛选 | 按语义相似度先筛候选工具 | 按初始查询一次性匹配，难以应对后续变化 |
| 主动声明 | 模型生成查询主动找工具 | 依赖模型判断 |
| 层次化匹配 | 工具按类别组织（搜索/读取/解析/查询） | 需人工分类 |
| **Skills 渐进式披露** | 只给工具名称索引，按需加载定义 | 最轻量 |

> 数据点：Anthropic 实验显示，按需检索方式使 Opus 4 在工具使用基准上准确率从 **49% → 74%**。
