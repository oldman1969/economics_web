## 1. 上下文：决定 Agent 能力上限的关键

### 1.1 天才工程师的比喻

> 一位天才工程师加入你的团队，理论功底深厚、编程能力卓越，但对你们的产品架构、业务逻辑、技术债务一无所知——他也难以发挥价值。

对 Coding Agent 而言，"修 bug"指令的上下文质量直接决定成败，需要三类信息：

| 信息类别 | 例子 | 缺了会怎样 |
|----------|------|-----------|
| 实时代码上下文 | 目录结构、模块职责、数据结构、代码规范 | 写出风格冲突甚至架构冲突的代码 |
| 流程规范 | Git 策略、提交规范、CI/CD | 直接往主分支提交未测试代码 |
| 环境信息 | 环境配置、数据库地址、部署方式 | 本地能跑通，测试环境崩溃 |

### 1.2 全章最重要的一句话

> **模型本身的智力只是基础，上下文的质量才是 Agent 能力的真正上限。**

一个中等模型配上精心组织的上下文，往往能胜过顶级模型在信息匮乏下的盲目摸索。

### 1.3 翁家翌的名言

> "人和模型一样，最重要的是 Context。""AI 短时间内无法取代人的最大原因也是 context——因为 AI 跟人并不在同一个环境里面。"

**推论**：构建 AI 原生团队，首先是一场**文档化运动**，而不只是部署新工具。团队是信息黑洞，再好的 Agent 也无计可施。Linux 内核三十年靠"透明、文档驱动"的协作，天然就是 AI 友好的环境。

## 2. API 上下文结构：四种消息角色

每次调用大模型都是**无状态**的——所有信息必须完整放进 messages 列表：

| 角色 | 含义 | 谁写 |
|------|------|------|
| `system` | 身份、规则、约束，最高优先级 | 开发者 |
| `user` | 终端用户的请求 | 用户 |
| `assistant` | 模型之前的回复（含工具调用） | 模型 |
| `tool` | 工具执行结果（经 tool_call_id 关联） | 框架 |

外加独立的 `tools` 字段（不是消息），告诉模型有哪些工具可用。

> 💡 这个结构是理解后续所有技术的底座——你的 [deep-dives/05 Transformer](deep-dives/05-Transformer架构.md) 讲了模型内部怎么算，这里讲的是**输入怎么组织**。

## 3. KV Cache 友好的上下文设计（核心）

### 3.1 先建立直觉

模型每生成一个 token，都要回头看前文所有 token 的中间结果。KV Cache 把前文算好的 K/V 向量缓存，下一轮只算新增 token。**前提是前缀完全不变——改一个字符，缓存全废，从头重算。**

### 3.2 时间戳的教训（全书最经典的故事）

某客服 Agent 每天处理 10 万次对话。工程师为了让它"知道当前时间"，在系统提示词里加了 `Current time: {{now}}`。结果：

```
首 token 延迟: 0.5 秒 → 3-5 秒
月度账单: 几乎翻倍
模型没换，代码看起来没问题——就一行时间戳
```

**原因**：那一行时间戳让系统提示词每次请求都不同 → KV Cache 每次全失效 → 从头重算整个前缀。

> ⚠️ 这种"无形成本"在 Agent 系统里反复出现——开发者写下一行看似无害的代码，可能让整条推理链路慢一个量级。

### 3.3 三条铁律（必须背下来）

1. **系统提示词和工具定义一旦确定就不要改**——多一个空格都导致缓存全废
2. **动态信息永远追加到末尾**——时间戳、用户状态作为新消息追加，而非改系统提示词
3. **用标准 API 格式，不要自行拼接消息**——结构化消息会被 Chat Template 翻译成模型训练时见过的固定序列；自己拼 "USER: ... ASSISTANT: ..." 会削弱模型的多步思考能力

### 3.4 常见错误模式（实验 2-3）

| 错误模式 | 危害 |
|----------|------|
| 动态系统提示词（嵌入时间戳） | 缓存全失效 |
| 动态用户配置 | 破坏缓存 |
| 工具定义动态排序 | 缓存失效（且固定顺序对选工具几乎无影响） |
| 滑动窗口对话历史 | 破坏前缀一致性 + 丢失关键工具结果 |
| 文本格式化（拼字符串） | 偏离训练格式，模型能力下降 |

### 3.5 KV Cache vs Prompt Cache（两个层级）

| | KV Cache | Prompt Cache |
|---|---|---|
| 层级 | 模型内部 | API 服务层 |
| 作用 | 加速单次请求内 token 生成 | 减少跨请求重复计算 |
| 计费 | 无 | 直接影响 API 账单 |

Prompt Cache 经济影响更大：Anthropic 需显式 `cache_control`，缓存读取约 1/10 价格，有最小长度（1024 token）和 TTL（~5 分钟）限制；OpenAI 自动前缀缓存。

> 这直接连到你的 [deep-dives/07](deep-dives/07-RLHF的数学.md) 之前学的 KV Cache——那篇讲了显存公式 `2×层数×维度×长度×字节`，这篇讲的是**工程上怎么避免让缓存失效**。

### 3.6 前沿：KV Cache 未必是一次性的

书里引用了作者自己的论文（Li Bojie, arXiv:2606.17107）：模型在 prefill 阶段其实在"做笔记"——把每个字段"意味着什么"的结论写进下游 KV，而非原样缓存。由此打开两种新操作：

- **编辑**：改一个字段后，顺着思考链传播修正，用 ~1% 算力得到与整段重算一致的结果
- **组合**：把预计算的"技能"缓存用 RoPE 挪到新位置拼接，O(L²) 重算降到 O(L) 拼接

> 这仍属研究阶段，但指向"上下文可变、缓存收益还在"的可能。生产环境仍应遵守三条铁律。

## 4. 缓存作为架构约束：Claude Code 的实践

当 Prompt Cache 经济效益足够显著时，缓存一致性会**反过来主导架构设计**：

1. **提示词结构由缓存边界决定** —— 系统提示词被缓存边界一分为二，边界前全局缓存、边界后放用户/会话特定信息。N 个二值条件放边界前 = 2^N 种缓存键变体，所以动态元素严格归到边界后。
2. **子 Agent 与父 Agent 字节级对齐** —— 子 Agent 的提示词、工具定义、前缀必须与父 Agent 逐字节匹配，才能命中 Prompt Cache。
3. **工具结果的替换字符串首次出现即冻结** —— 保证会话恢复后与缓存字节流一致。

> 💡 核心启示：**缓存经济性不是事后优化，而是前置约束。** 越早纳入架构设计，后续代价越小。

## 5. Skills：渐进式披露

系统提示词塞满所有场景 → 两个问题：**浪费 token**（大部分内容无关）+ **注意力稀释**（无关信息过多，见第 7 节"上下文腐化"）。

Skills 的解法：**按需加载，而非一次性塞满**。三层结构：

```
第一层 元数据（启动时加载，~300 tokens）
  只有 name + description，作为"目录"注入上下文

第二层 SKILL.md 核心流程（按需加载，~2K tokens）
  任务触发时用 Skill 工具加载完整流程

第三层 子文档（选择性深入）
  html2pptx.md、reference.md、scripts/*.py
```

**description 是路由决策的关键**，写法应是**路由条件而非功能介绍**：

```
好: "Use when 用户需要从内容生成 PPT；Don't use when 只是提取文本"
坏: "help with backend"（任何后端工作都触发，路由失准）
```

> 书里反复强调：**"何时该用我"比"我能做什么"重要得多**；反例不是可选项，而是路由准确的关键。你项目里那一堆 skills（gen-srs、md-to-word 等）正是这套机制的实例。

## 6. Agent 状态栏：检索而非推理

### 6.1 问题

Agent 执行复杂任务容易陷入：无限循环、状态遗忘、目标偏离。根源是**缺乏对当前状态的感知**。

### 6.2 状态栏是什么

在上下文末尾注入结构化的元信息摘要（不是对话主体）：

```xml
<agent_status>
  phone_call 已调用 3 次 (Xfinity: 3)
  约束检查: 已达上限 (3/3) ✗
  TODO: [✓]联系Xfinity [✓]确认降价
  当前时间: 2025-09-14 10:30
  当前状态: 等待用户确认
</agent_status>
```

**系统提示词 = 入职时发的员工手册**（不变）；**状态栏 = 屏幕边缘的实时仪表盘**（持续更新）。

### 6.3 理论基础：检索而非推理

这是全书最深刻的理论洞察之一：

> **注意力机制擅长在已有内容里"查找"，却不擅长在一次前向传播里主动"归纳统计"。**

- 问"笼子 37 里是什么猫" → 模型秒答（检索）
- 问"黑猫白猫各多少只"（100 个笼子记录）→ 不启用思维链时答错（这是统计归纳，是思考）

**工程含义**：把需要"思考"才能得到的结论，预先算好写进上下文，让模型直接"检索"到。状态栏就是"把算好的结论加进上下文"。

## 7. 上下文压缩：腐化与提炼

### 7.1 两个动机

1. **长度/成本约束**（直观）—— 窗口有限、token 越贵
2. **提升思考质量**（深层）—— 总结后的知识比原始形式更利于模型使用

### 7.2 上下文腐化（Context Rot）

区别于"溢出"（装不下）：**腐化是"装得下但找不到了"**——窗口没满，但 Agent 突然找不到关键信息，或反复纠结已解决的问题。

根源：注意力权重被分散到更多 token，无关内容占大头时，决策质量悄然下降。**最常见的失效模式不是窗口不够长，而是信息密度不对。**

### 7.3 Karpathy 的洞察

> 模型的"记忆差"某种程度上是特性而非缺陷——窗口有限性迫使模型学会从细节中抽象出一般模式。

### 7.4 压缩与 KV Cache 的互补

看似矛盾（压缩要改中间内容，KV Cache 要前缀不变），实则互补：

1. System Prompt 和 Tool Definitions **永远不动**（静态前缀持续缓存）
2. 压缩对象是**对话历史里的 tool results**（替换位置之后的缓存失效，之前的仍有效）
3. 权衡：不压缩→窗口溢出失败；压缩→损失部分缓存但信息密度更高。**最好在接近阈值时批量压缩，而非每轮都压**

## 📌 本章要点

1. **上下文质量决定 Agent 能力上限**，不是模型参数——"人和模型一样，最重要的是 Context"
2. **三条铁律**：系统提示词/工具定义别改、动态信息追加末尾、用标准 API 格式
3. KV Cache（模型内）vs Prompt Cache（API 层），后者经济影响更大
4. 缓存经济性是**架构前置约束**，不是事后优化（Claude Code 实践）
5. Skills 靠渐进式披露省 token、防注意力稀释；description 要写"何时用"而非"能干什么"
6. Agent 状态栏弥补模型"检索而非推理"的短板——把算好的结论注入上下文
7. 压缩双动机：省 token + 提质量；警惕"上下文腐化"（装得下但找不到）
