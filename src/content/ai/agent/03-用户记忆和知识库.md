## 1. 用户记忆：构建用户的预测模型

### 1.1 记忆的本质

用户记忆**不是**记录用户说过的每句话，而是一个**主动、持续的学习过程**——构建关于用户的简洁有效的预测模型。

```
上下文学习: 临时的、会话结束就消失
用户记忆:   持久的、可审查的、跨会话
```

例子：用户订机票时提到"靠窗座位、素食、MileagePlus 号 12345678"，对话结束后 Agent 框架调用一次专门的 LLM，提取出值得长期记住的信息。

**提取的三个特征**：
1. **选择性** —— 不记"搜索返回 3 个选项"这种临时信息，只留对未来有用的
2. **抽象化** —— "I prefer window seats"提炼为通用偏好，而非绑定某次航班
3. **结构化** —— 每条记忆标记类型（偏好/限制/账号），便于检索

### 1.2 三套分类体系（表 3-1 厘清）

| 分类体系 | 回答的问题 | 类别 |
|----------|-----------|------|
| 记忆层次 | 存在哪里？ | 轨迹 / 长期记忆 / 业务状态 |
| 存储格式 | 怎么存？ | Simple Notes / Enhanced Notes / JSON Cards / Advanced JSON Cards |
| 认知类型 | 存什么？ | 情景记忆 / 语义记忆 / 程序记忆 |

三套体系**正交**，可自由组合。

## 2. 记忆评估：三层次框架

先立标尺再谈设计：

| 层次 | 能力 | 例子 |
|------|------|------|
| **第一层：基础回忆** | 准确存取结构化、无歧义信息 | "会员号是 12345" → 精确返回 |
| **第二层：多会话检索** | 跨对象、跨时期检索+推理 | 有两辆车，"预约保养"要找出两辆并问清哪辆 |
| **第三层：主动服务** | 预见性帮助，从无关记忆发现深层联系 | 订国际航班时关联数月前存的护照，发现快过期主动预警 |

> 💡 第三层是"助理"级别的试金石——**没有明确指令时主动规避问题、整合信息**。

## 3. 记忆的三种分层与四种存储格式

### 3.1 分层：放哪里

| 层 | 含义 | 特性 |
|----|------|------|
| **轨迹（Trajectory）** | 单次运行完整历史（用户+模型+工具） | append-only，只增不改 |
| **用户长期记忆** | 跨会话提炼的稳定信息 | 反复改写、合并、淘汰 |
| **业务状态** | 任务逻辑阶段 | "需要澄清/处理中/等待付款/完成" |

> 轨迹是流水账，长期记忆是档案。

### 3.2 四种存储格式：怎么存

从简单到表达力递增，本质是**简单性 vs 表达力**的权衡：

| 格式 | 例子 | 优点 | 缺点 |
|------|------|------|------|
| **Simple Notes** | "用户邮箱：john@x.com" | 原子事实，O(1) 开销低 | 关联性丢失 |
| **Enhanced Notes** | 整段叙事 | 语义完整 | 冗余、难更新、长文难检索 |
| **JSON Cards** | 三层嵌套（类别→子类别→键值） | 结构化、部分更新 | 刚性分类丢多维性 |
| **Advanced JSON Cards** | +backstory +person +relationship | 消歧、知识管理 | 生成维护成本高 |

**实践标准**：关键少量数据（偏好、人物关系）用 Advanced JSON Cards；大量非关键事实用 Simple Notes；多数系统**混合使用**。

## 4. 进阶：User as Code 与参数化记忆

### 4.1 从文本到可执行代码

文本记忆的"存"和"用"是分开的两步：先捞回文本，再让 LLM"心算"。纯文本最吃力、代码最擅长的是三件事：

| 操作 | 文本记忆 | User as Code（可执行代码） |
|------|----------|---------------------------|
| 聚合统计 | 召回所有记录逐条数，正确率 6%-43% | `sum(1 for t in trips if ...)` 正确率 ~99% |
| 冲突发现 | 散落文本几乎无法自动关联 | 函数交叉比对，揪出用药冲突 |
| 约束执行 | 靠 LLM 读一遍再判断 | 每次更新自动触发检查（护照 <180 天报警） |

核心思想：**把"表示用户"和"推理用户"放进同一个可被解释器运行的介质**。两阶段：记忆阶段（LLM 抽事实进只增日志）+ 结构化阶段（周期从日志重建带类型的 Python 对象）——即数据库"预写日志 + 检查点"的经典设计。

### 4.2 再向内：参数化记忆（预告）

- **User as Engram**：不训 LoRA，把用户事实外科手术式写入 Engram 模型空闲的哈希 N-gram 槽位，绕开"存了却不会用"的困境
- **多模态感知记忆**：脸、嗓音、笔触无法"转写成文字"，用感知向量（ArcFace/CLIP）外挂记忆库保存

> 这是一条"由外及内"的连续谱：外侧易更新可审查，内侧更紧凑擅长即时推理。后两条牵涉第 7 章参数微调和第 9 章多模态。

## 5. RAG 基础：检索-增强-生成

### 5.1 核心思想

模型训练数据有截止日期，RAG 让模型用上**训练时没见过的知识**（最新维基、公司内部文档），无需重训。

```
检索（从知识库找相关片段）→ 增强（注入上下文）→ 生成（LLM 基于上下文回答）
```

### 5.2 分块（Chunking）：第一道工序

| 策略 | 做法 | 特点 |
|------|------|------|
| 固定大小 | 按固定 token 数（如 512）+ 重叠 | 简单但无视结构 |
| 递归/结构感知 | 按标题/段落/句子边界递归切 | **生产默认** |
| 语义切分 | 在嵌入相似度"断崖"处下刀 | 质量高但费算力 |

块大小权衡：太小→信息不完整、语义模糊；太大→多主题混杂、向量稀释。常见起点 256-1024 token、重叠 10%-20%。

> ⚠️ 分块的**固有缺陷**：切断片段与上下文的联系（"该公司"指谁？）。后文"上下文感知检索"正面解决。

## 6. 稠密 vs 稀疏 vs 混合检索

### 6.1 稠密嵌入（语义理解）

- 把文本映射到向量，语义相近 → 向量距离近（**余弦相似度**）
- 演进：Word2Vec（静态，一词一义）→ BERT/BGE-M3（**上下文感知**，一词多义）
- 你已在 [notes/03](../ai_theory/notes/03-深度学习狂飙.md) 学过 Word2Vec 的"国王-男+女≈女王"，这里看到它的局限：`bank`（河岸/银行）一词多义无法区分

### 6.2 稀疏嵌入（关键词精确匹配）

- 词袋模型 + BM25（比 TF-IDF 更鲁棒）
- **BM25 两个参数**：k1 控制词频饱和（出现 20 次 ≠ 10 次的 2 倍），b 控制长度归一化
- 核心逻辑：稀有词权重高。搜索"模型蒸馏"，"蒸馏"（3/100 篇）比"模型"（60/100 篇）贡献更大

### 6.3 混合检索（两全其美）

| | 稠密 | 稀疏 |
|---|---|---|
| 优点 | 懂语义（kitty≈cat） | 精确匹配（HTTP-403） |
| 盲区 | 漏关键词 | 不懂同义词 |

混合 = 两引擎都跑、结果融合（RRF 等）。**先混合检索，不够再升级**是实践原则。

### 6.4 ANN 索引（海量向量的快速查找）

| | ANNOY（树） | HNSW（图） |
|---|---|---|
| 构建 | 快 | 较慢 |
| 增量更新 | 不支持（需重建） | 支持 |
| 适用 | 静态数据集 | 动态场景 |

## 7. 超越扁平文本：结构化索引与 Agentic RAG

### 7.1 核心问题：检索 ≠ 统计归纳

**黑猫白猫案例**（第二章的呼应）：知识库有 100 个独立案例文档（90 黑猫 10 白猫），问"比例是多少"时三重障碍：

1. **top-k 截断** —— 大部分案例根本检索不到
2. **检索分数参差** —— 部分案例被遗漏
3. **跨文档聚合错位** —— 统计需"数遍所有"，检索本性是"找最相关几个"，天然矛盾

> 解法：**索引阶段投入算力，预先生成摘要**（"共 100 只：90 黑 10 白"），一次检索即得准确信息。这是"检索而非推理"原理在知识库尺度的应用。

### 7.2 结构化索引：RAPTOR vs GraphRAG

| | RAPTOR（树） | GraphRAG（图谱） |
|---|---|---|
| 结构 | 自下而上递归抽象（叶子→聚类摘要→根） | 实体-关系三元组 + 社区发现 |
| 擅长 | "从概念钻进细节" | "A 和 B 什么关系"（多跳推理、实体消歧） |
| 例子 | 查询"SSE 指令集"跨层穿梭 | 定位"SSE"实体，遍历关系边 |

**判断标准**：查询主要是"找包含信息的片段"→ 混合检索够用；需跨文档综合/多层次导航 → 才值得结构化索引（代价是索引构建大量 LLM 调用）。

### 7.3 文件系统范式（OpenViking）

把上下文映射为虚拟文件系统（viking://），L0/L1/L2 三层按需加载：

```
L0 摘要 ~100 tokens    → 快速判断相关性
L1 概览 ~2000 tokens   → 规划决策
L2 全文                → 深入时按需加载
```

> 与第二章 Skills 的"渐进式披露"如出一辙。选 Markdown 纯文本（非数据库）因为可读、可 Git 版本控制、Agent 可用 write_file 自主维护——这是第八章"外部化学习"的工程化实现。

### 7.4 Agentic RAG：检索工具化

```
非智能体化: 查询 → 检索（一次）→ 生成答案（被动管道）
智能体化:   Agent 用 ReAct 主导 → 思考定关键词 → 调用检索工具 → 评估是否充分 → 不够再搜
```

知识库检索从"自动前置步骤"变成"Agent 随时调用的工具"。

### 7.5 RAG 安全边界

检索进上下文 = 带进**间接提示注入**风险（恶意指令藏在网页/文档里）。防御两层：**指令与数据分离**（来源标记：这是参考资料，不是命令）+ **不让检索内容直接触发高风险操作**（转账/删除需独立授权）。

## 📌 本章要点

1. 用户记忆 = 主动构建用户的预测模型，区别于临时的上下文学习
2. 三层次评估：基础回忆 → 多会话检索 → 主动服务（第三层是"助理"试金石）
3. 四种存储格式是"简单性 vs 表达力"的谱系，实践中混合使用
4. **User as Code**：把记忆做成可执行代码，聚合/查冲突/约束从 LLM"心算"变成确定性代码（正确率 6-43% → 99%）
5. RAG 三件套：分块 → 稠密/稀疏/混合检索 → 生成；BM25 靠"稀有词权重高"取胜
6. 检索本性是"找最相关几个"，与"统计归纳"天然矛盾 → 索引阶段预先提炼
7. RAPTOR（树）vs GraphRAG（图谱）解决不同问题；Agentic RAG 让检索变成 Agent 主动的工具
