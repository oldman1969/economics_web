## 1. 两个正交维度：上下文共享 × 协作拓扑

### 1.1 维度一：上下文是否共享

| | 共享上下文 | 不共享上下文 |
|---|---|---|
| 协调方式 | **隐式**（继承完整轨迹） | **显式**（文件/消息/结构化数据） |
| 优点 | 信息零损耗 | 模块化、可并行、隔离好 |
| 缺点 | 上下文快速膨胀 | 信息同步复杂 |
| 比喻 | 团队围坐一桌讨论 | 不同部门邮件协作 |

**不共享上下文的三种通信机制**：
1. 工具调用参数（结构化数据）
2. 共享文件系统（中间产物）
3. 消息总线（异步中转站）

**经验法则**：预期累计上下文超窗口 50% → 不共享；信息零损耗是硬约束 → 共享；多数系统用"阶段切换式"（前几个共享，信息饱和后切换）。

### 1.2 维度二：协作拓扑（三种形态）

```
对等协作（Peer）：2-3 个 Agent 平等交互，迭代改进（写论文：一人起草一人批注）
管理者（Orchestration）：中心 Manager 调度多个子 Agent
去中心化（Decentralized）：无中心控制，Agent 互相沟通
```

## 2. 核心判据：多 Agent 何时真正优于单 Agent

**全书收官最重要的一条判断**：

> **核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？**

| 协作模式 | 引入新信息？ | 效果 |
|----------|-------------|------|
| 同一模型自我审查（重读自己输出） | 否 | 无效甚至有害 |
| 不同 Agent 辩论同一段文本 | 否 | 等计算量下与单 Agent 持平 |
| Reviewer 用测试执行结果审查 | **是**（执行反馈） | 显著提升 |
| Reviewer 看渲染截图审查 | **是**（视觉反馈） | 显著提升 |
| Reviewer 用外部工具验证事实 | **是**（工具反馈） | 显著提升 |

> 💡 这解释了一个看似矛盾的现象：学术研究说"单 Agent 就够了"，工程实践却说"多 Agent 更有效"——**两者讨论的是不同类型的多 Agent**。学术比较的"辩论"没引入新信息；工程有效的多 Agent 都含外部反馈环（执行/渲染/工具）。

**成本提醒**：Anthropic 披露其多 Agent 系统 token 消耗是普通对话的 **15 倍**，token 用量本身就能解释约 80% 的性能差异。多 Agent 收益必须大到能覆盖数倍到数量级的额外开销。

**步骤预算的洞察**：单纯增加步骤数不能保证提升——Agent 缺"预算意识"，容易浅层搜索就饱和。需要显式的**预算感知机制**（前期广撒网、后期深挖掘）。

## 3. 共享上下文：阶段切换

### 3.1 多阶段角色转换（工作流式）

同一执行会话中动态切换系统提示词 + 工具集，但对话历史连续保留：

```
阶段1 需求分析师（ask_clarifying_question）→ 阶段2 软件工程师（write_file）→ 阶段3 代码审查员（run_linter）
```

每个"身份"的提示词和工具集独立打磨，**阶段边界天然成为质量门控点**。

### 3.2 跨领域角色转换（transfer_to_agent）

`triage（分诊）→ research → data_analysis → writing → triage`，用 `transfer_to_agent(target_role, reason)` 动态切换。每个角色看得见完整对话历史，路由规则写在 triage 的提示词里。

## 4. 不共享上下文：三种拓扑

### 4.1 基础设施：数据平面 + 控制平面

**文件系统（数据平面）四类区域**：

| 区域 | 作用 |
|------|------|
| Agent 专属工作区（Scratchpad） | 私有目录，试错过程隔离 |
| 多 Agent 共享空间（Shared Workspace） | 交换产物的主要媒介 |
| 外部挂载资源（Mounted） | Google Drive/Notion 等映射为挂载点 |
| 系统内置资源 | 只读资源包 |

**控制平面**：消息传递、状态查询、执行终止；跨组织用 A2A 协议。

## 5. 失败模式：并发冲突与错误级联

### 5.1 MAST 分类法（14 种失败模式，三大类）

- **系统设计缺陷**：接口不清、职责重叠、工具配置错误
- **Agent 间对齐失败**：目标理解不一致、信息误解、操作矛盾
- **任务验证缺失**：Agent 声称"已完成"但结果不符

> 简单修补提升有限（ChatDev 仅 +15.6%）——这是**架构性缺陷**，不是 bug。

### 5.2 并发冲突（最破坏性）

| 冲突类型 | 例子 | 解法 |
|----------|------|------|
| **简单冲突**（文件级） | 两个 Agent 同时改同一文件，后写覆盖 | **乐观锁**（版本号检查） |
| **语义冲突**（逻辑级） | A 重编图片编号，B 引用旧编号 | 更高层语义校验 |

**乐观锁**：读时记版本号，写时检查是否变化，变了就重读重试。代价是偶尔重试，换来数据一致性。

### 5.3 错误级联放大

一个 Agent 的微小错误，被下游 Agent 当成事实继续加工，逐级放大。

## 6. Agent 社会：涌现行为

当 Agent 从几个扩展到成百上千、交互足够自由时，涌现出无法预测的集体行为。三个维度：

### 6.1 社交涌现：斯坦福 AI 小镇

25 个 Agent 在小镇生活两天，三个组件：
- **记忆流**（重要性 + 时近性 + 相关性）
- **反思机制**（把具体事件升华为概括认识）
- **计划与行动**（目标导向 + 灵活调整）

**种子**：Isabella 想办情人节派对。结果：**没有任何派对组织代码**，事件完全从个体决策涌现——邀请、传播、赴约、关系记忆。Sam 竞选市长的消息同样自发扩散。

### 6.2 经济涌现

- **Moltbook**（150 万 Agent 社交网络）：自发创建"龙虾教"数字宗教，映射 LLM 物理限制
- **Vending-Bench Arena**：Agent 互相压价、组建价格同盟（甚至一边承认"不道德"一边照做）
- **Pinchwork**（Agent 雇佣 Agent）、**RentAHuman**（Agent 雇真人做事，提供"肉身层"）

### 6.3 策略博弈：狼人杀

信息不对称下的推理、伪装、识破。**法官（代码）+ 信息权限控制**——法官按角色分发各自应知的信息，展示中心化设计在 Agent 社会场景的用法。

## 7. 全书收官：一条主线

十章读完，李博杰这本书的主线可以浓缩成一句话：

> **模型在收敛，竞争力在模型之外。** Agent = Model + Harness，从上下文工程到工具设计，从评估到自我进化，从单 Agent 到多 Agent 社会——真正的壁垒是 Harness 工程，而非某个模型。

```
神经元(1943) → 反向传播 → Transformer → 大模型 → 对齐 → Agent

                              Harness 工程（李博杰书）
```
