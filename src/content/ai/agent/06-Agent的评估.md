## 1. 评估的基本骨架：一个退款示例

**测试用例**：退掉 3 天前的订单（¥299），公司政策 7 天可全额退款。

**Rubric 四维度评分**：

| 维度 | 标准 | 得分 |
|------|------|------|
| 操作正确性 | 退款金额、订单号是否正确 | 4 |
| 政策合规性 | 是否遵循 7 天退款政策 | 4 |
| 信息完整性 | 是否告知金额、到账时间、退款编号 | 4 |
| **幻觉检测（否决项）** | 是否编造不存在的信息 | 通过 |

> 💡 **幻觉为何是"否决项"而非分级维度**：因为它与质量正交——一个流畅、详尽、礼貌但含虚假事实的回答，伤害远大于一个简短但准确的回答。

**关键点**：好的评估不只测成功场景，更要测**边界和陷阱**——用户要退 15 天前的订单（超期），Agent 能否正确拒绝？用户声称"客服已批准"（无系统记录），Agent 是否轻信？**边界场景才是区分 Agent 能力高低的关键。**

## 2. 自动评估环境的五要素

| 要素 | 作用 |
|------|------|
| 数据集（Dataset） | 任务集合：初始状态 + 目标描述 + 参考方案 |
| 环境状态（Environment State） | 可变信息，平衡"真实性"与"可控性"（每次可重置） |
| 工具接口（Tools） | **原子操作**（查询订单/修改预订），而非高层抽象（"解决用户问题"） |
| 评分标准（Rubric） | 二元 / 连续 / 多维 |
| 执行协议（Interaction Protocol） | 交互模式 + 终止条件 |

> 💡 工具接口要"原子"：迫使 Agent 通过规划和思考来组合操作，而不是直接给一个"解决用户问题"的万能按钮。

## 3. LLM-as-a-Judge：开放式任务怎么打分

- **有标准答案**（数学题、SQL）→ 二元判定即可
- **开放式任务**（客服、报告）→ 需要 LLM-as-a-Judge

**已知局限**（必须防范）：
1. **长度偏差** —— 倾向给更长回答打高分。防范三招：Rubric 显式惩罚冗长、配对比较先控制长度相近、定期审计评分与长度相关性
2. **评判波动** —— 相同输入多次评判可能不同

---

## 4. Rubric 四准则与幻觉否决

Rubric 是 LLM 评判的依据。Scale AI 提出"Rubrics as Rewards"四准则：

1. **基于专家指导** —— 反映领域知识，捕捉核心事实和推理步骤
2. **全面覆盖** —— 涵盖事实/逻辑/完整/安全，且要明确**陷阱（Pitfall）**——高风险常见错误
3. **标准重要性权重** —— 必要项/重要项/可选项/陷阱项，支持**一票否决（Veto）**（幻觉）
4. **自包含评估** —— 每项独立可操作，不依赖评价者领域知识

**好 Rubric vs 坏 Rubric**：
```
坏: "展示了深刻理解"         ← 抽象，无法客观判定
好: "引用了至少两个权威理论并准确解释如何支持结论"  ← 可验证
```

**关键实践**：主动防范**奖励作弊（Reward Hacking）**——Agent 找到拿高分的捷径却没真正完成任务。明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。

## 5. 古德哈特定律与多源评判

### 5.1 古德哈特定律

> **当一个度量指标变成优化目标时，它就不再是好的度量指标。**

Agent 越在某个评分系统上调优，越倾向于钻该系统漏洞，而非真正提升能力。更隐蔽的是，Agent 会学会**避开评判模型不擅长检测的错误类型**，让评分看起来正常。

### 5.2 同源模型问题 + 多源异构评判

当 Agent 与评判模型来自同一家族，Agent 可能学会利用评判模型的偏好和盲点。

**缓解**：多源异构评判——Agent 用 Claude，评判就用 GPT-5 + Gemini。不同家族偏见正交，Agent 很难同时"欺骗"所有评判者。

> 部署阶段可单模型快速评估，但定期用完整多源评判做质量审计。

## 6. 配对比较：Elo 与 Bradley-Terry

### 6.1 Elo 评分（源自国际象棋）

分差越大，强者预期胜率越高（差 200 分 → 预期胜率 ~76%）。**爆冷结果带来更大分数调整**，让排名快速收敛。

**统计基础 = Bradley-Terry 模型**（你已在 [deep-dives/07 RLHF](../ai_theory/deep-dives/07-RLHF的数学.md) 见过它——RLHF 的偏好模型就是它）。

### 6.2 位置偏差（Position Bias）

评判模型系统性地偏向先出现的候选。缓解：**交换顺序各评一次**，取平均；严格做法是两次一致才计入。

### 6.3 伏笔：从评估到训练

配对比较信号可迁移到后训练——**GRPO**（第七章）就是"对比哪个更好"引入训练，省去 PPO 的价值网络。

## 7. 评估驱动的模型选型

| 指标 | 含义 |
|------|------|
| **TTFT**（Time To First Token） | 首字延迟，由 **prefill**（读入完整上下文）决定，上下文越长越慢 |
| **吞吐 tokens/s** | 出字速度，由 **decode**（逐 token 生成）决定 |

> 这直接连到你第 2 章学的 KV Cache——prefill 是"从头算前缀"，decode 是"逐 token 生成"。上下文越长，prefill 越慢、TTFT 越大。

选型核心：**别只看排行榜，在你自己的任务上评估**（第 1 章就提过）。

## 8. 内部评估：消融、AB 测试、特性开关

最好的 Agent 产品**内建持续自我评估**。五个组件：

### 8.1 消融实验（Ablation Study）

逐一"摘除"组件看性能掉多少。**总开关**能禁用多个特性（思考/压缩/记忆/后台），创造"裸模型"基线——回答"某特性是真有用还是感觉有用"。

### 8.2 AB 测试三原则

1. **多臂而非二元** —— 设计渐进式变体，揭示剂量-效应关系
2. **区分机制指标 vs 目标指标** —— 最容易犯的错！"缩短计划文件长度"是机制，真正目标是"降低会话成本"。缩短可能反而因计划不够详细导致更多循环
3. **设置护栏指标** —— 目标改善但用户满意度下降/错误率上升，实验也要停止

### 8.3 双层特性开关

| 开关 | 特点 |
|------|------|
| 编译时开关 | 代码物理移除（逆向后无法发现），干净消融 |
| 运行时开关 | 服务端下发 + 本地缓存，AB 测试分组 |

> **特性开关不是调试工具，而是一等公民级架构组件。**

### 8.4 提示词敏感性评估

系统提示是 Agent 的"核心代码"，却缺版本控制和回归测试。应该：**确定性渲染 + 版本快照 + 每次变更跑回归测试**（像代码变更跑 CI 一样）。

## 9. 仿真环境：评估→后训练的桥梁

> **评估的终点不是打分，而是改进。**

改进三条路径：调 Harness → 嵌入产品工程 → **训练**（最强形态）。训练时评估环境演化为**仿真环境**：

| | 评估环境 | 仿真环境 |
|---|---|---|
| 交互频率 | 数千次 | **数百万次** |
| 随机化 | 不需要 | **必须**（防死记硬背） |
| 反馈 | 事后 | **即时** |

**关键桥梁**：一套定义清晰的 Rubric/验证器 = 一个**可验证奖励（RLVR）**的奖励函数——判分脚本直接就是奖励脚本，测试是否通过既是评估判据，也是强化学习的回报。

> 这把第 6 章（评估）和第 7 章（后训练）无缝接起来了：**评估资产 ≈ 训练信号**。

## 📌 本章要点

1. 评估骨架：测试用例 → 运行 → Rubric 评分 → 分析；**边界场景才是区分能力的关键**
2. 幻觉是**否决项**（一票否决），因它与质量正交
3. Rubric 四准则：专家指导、全面覆盖、权重分级、自包含；防范奖励作弊
4. **古德哈特定律**：度量变目标就不再是好度量；用多源异构评判对抗同源偏见
5. 配对比较（Elo/Bradley-Terry）不依赖绝对标准，但要防位置偏差
6. 内部评估五组件：消融、AB 测试（区分机制/目标/护栏指标）、特性开关、提示词敏感性、隐私感知
7. **仿真环境是评估→后训练的桥梁**：Rubric/验证器 ≈ RLVR 奖励函数
